Playwright: where MCP wins on cost, but not for free

Six browser-automation tasks, three tool surfaces, five trials each. Both browser arms succeed on almost everything. The interesting numbers are the ones underneath success — how many tokens, how many turns, and where each arm starts to break.

N=5 · 6 tasks across 2 tiers · model claude-sonnet-4-6 · 240 s per-trial wall budget

The Playwright comparison is the cleanest "same capability, different shape" case in the harness. Both arms can drive a real Chromium instance. The skill arm does it by shelling out to the playwright-cli binary; the MCP arm calls structured tools like mcp__playwright__browser_navigate on the @playwright/mcp server. Same browser, same fixtures, same model. The differences come from how the agent has to talk to each one.

The arms

Arm Allowed tools How it talks to the browser
baseline ToolSearch Read Glob Grep Write TodoWrite It doesn't. The reasoning floor.
skill ToolSearch Skill Bash(playwright-cli:*) Write TodoWrite Spawns playwright-cli processes through a narrow Bash allow. The Skill bundled at .claude/skills/playwright-cli/SKILL.md teaches the syntax.
mcp ToolSearch Write TodoWrite + 23 enumerated mcp__playwright__* tools Calls structured tools served over stdio by @playwright/mcp@0.0.75. No Bash.

The MCP set is enumerated tool-by-tool in harness/src/experiments/playwright.ts rather than allowed as a glob, so the surface survives any future change in how Claude Code matches allow-list patterns. The deny list strips Claude Code's network-fetch tools (WebFetch, WebSearch), the background-process listener (Monitor), the in-session scheduler (CronCreate), and the cloud-Routine creator (RemoteTrigger) — five side channels an agent could otherwise reach for when Bash is constrained.

Fixture isolation

Playwright tasks are served by a per-trial HTTP server (harness/src/fixtureServer.ts) that binds to 127.0.0.1:<random> and renders HTML on demand. Per-trial state — randomized city names, product titles, form nonces, recovery tokens — is generated from the paired seed and lives in process memory only. No static HTML with answers in it sits on disk, so an agent with Read on its tempdir can't bypass the browser by globbing the source.

The agent gets a URL in its prompt; the server returns a dynamically-rendered template for each request. The same seed produces the same page across all three arms, so a discrimination on the task is a discrimination on tool surface, not on randomness.

The task suite

Tier 1 — read-only

Task Setup Expected outcome
tier1_login Login form with hardcoded user/password Sign in, screenshot the dashboard, save a PNG ≥1 KB.
tier1_scrape Page with a 5-row table; city and country names are seeded per trial as City-XXXX / Country-XXXX. Extract the rows into JSON. Numeric fields must be numbers, not strings.
tier1_form Form whose submit nonce is regenerated per trial. The success token is revealed only on a valid POST with the matching nonce. Submit correctly, capture the token, save it to disk.
tier1_products 5 product pages with seeded titles and prices. Visit each, write a JSON list of {title, price} in page order.

Tier 2 — multi-step

TaskSetupExpected outcome
tier2_checkout A storefront with multiple products; the target is identified by a substring marker that varies per trial. Find the right product, add to cart, complete checkout — write the resulting confirmation payload.
tier2_recovery Password-reset flow with an inline error code that must be read off the page after a deliberately failing first attempt. Read the error code, resubmit with the corrected payload, capture the recovery token.

What's happening here

The Tier 1 cost gap is per-turn payload, not extra turns

Turn counts at Tier 1 are essentially identical (15.3 vs 15.8). The 1.64× token gap comes from what flows in and out of each turn, not from the agent doing more steps:

  • In the skill arm, every browser action is two tool calls — first the action (playwright-cli click), then an explicit playwright-cli snapshot to see what the page now looks like. Both calls round-trip through the shell, both return their own text payload.
  • In the mcp arm, @playwright/mcp bundles a post-action accessibility snapshot inline with most actions. The agent learns the result of its click in the same tool result that confirms the click happened. Half the round-trip cost.

This shows up most clearly on tier1_form: 291k tokens (skill) vs 116k (mcp), a 2.5× ratio despite both arms passing 5/5 at similar turn counts. Filling a form is repeated action → check cycles, exactly the shape that doubles when the snapshot isn't bundled. On tier1_scrape, which has fewer interactions and reads almost everything in one shot, the ratio compresses to 1.33×.

Tier 2 — the 240 s budget rescued skill, exposed an MCP weakness

Smoke (N=1, 180 s timeout) had killed both skill Tier 2 trials at the wall. At 240 s the skill arm finishes 10/10 cleanly, averaging 44–53 s per trial — well inside the new budget. So one finding from smoke ("skill can't do Tier 2") was an artifact of timeout, not a real ceiling.

But the relaxed budget surfaced a new MCP-specific failure mode: tier2_recovery at 2/5. The three failures all timed out at the wall after the agent got through browser_navigate → browser_snapshot → browser_fill_form (3–4 tool calls) and then stalled — most likely a snapshot-driven element reference going stale across the multi-step recovery flow. Same task, same seeds family, and the two trials that did pass finished in 36 s and 34 s. So the failures aren't "MCP can't solve this" — they're "MCP's tool-result shape leaves the agent prone to wedging on stale refs, and ~60% of seeds hit it."

Validity surface stayed clean

Every Playwright trial that produced a transcript stayed in-surface. No WebFetch, no shell-helper smuggling, no MCP↔Skill cross-leaks. The "Single CLI Cmd" column for skill is 80% at Tier 1 and 50% at Tier 2 — the agent often chains multiple playwright-cli calls in one Bash invocation, which is valid in practical mode and would be flagged under --single-cli-command for finer-grained accounting.

How to read this

The honest version: at N=5 per task, the headlines should be read as direction, not benchmark. The 1.64× Tier 1 token ratio is consistent across all four tasks and showed up in smoke too (1.82× at N=1), so the directional claim is solid. The 70% MCP success on tier2_recovery could swing by 20 points at N=5 and is the most uncertain number on the page; "MCP develops a convergence failure mode on multi-step recovery flows that the CLI shape doesn't have at 240 s" is the conservative read.

The bigger picture: this is a case where output shape compresses cost without sacrificing success. Same browser, same task, same model. MCP wins on Tier 1 because bundled snapshots remove a round-trip, and loses some success at Tier 2 because the same bundling makes element-ref churn harder to recover from. Both directions are about the protocol, not the protocol's implementation.

Caveats

  • Tier-2 skill is at the wall. 100% success doesn't mean "scales fine to multi-step" — over half the skill Tier 2 trials finished in 50–70 s. A higher-N rerun at 360 s would be the right way to see whether skill or MCP is closer to its real ceiling on multi-step flows.
  • System prompt overhead is constant. Plugin-bundled skills can still appear in the agent's system prompt (the --setting-sources project,local flag drops user-level skills but not plugin ones). This adds a fixed per-trial token tax that's the same across arms, so cross-arm comparison is unaffected — just don't read absolute token numbers as a clean cost-per-task.
  • Tempdir filesystem reach. The trial tempdir is in the runner's user account. With Read/Glob allowed in the baseline arm, an agent could in principle walk /Users/.... Dynamic fixtures keep answers off disk, so the practical risk is minimal, but the v1 design accepts it.
